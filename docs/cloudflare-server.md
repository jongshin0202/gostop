# Cloudflare authoritative room server

The Vercel/static frontend remains independent. Cloudflare runs only the `gostop-authority` Worker and its `GameRoom` Durable Objects. One object, addressed by a 14-character Crockford-style random room code (70 bits), owns one two-player room. There is no matchmaking, spectator, leaderboard, or multiplayer-rules expansion in this milestone.

## Local development and deployment

```sh
npm install
npm run server:dev
```

The checked-in `runtime-config.js` deliberately leaves Online unavailable while keeping Solo usable. For local Online development, generate the public configuration and start the Worker:

```sh
GOSTOP_SERVER_URL=http://localhost:8787 npm run config:write
npm run server:dev
```

For deployment, authenticate without committing a token and deploy:

```sh
npx wrangler login
npm run server:deploy
```

After Wrangler prints the Worker URL, configure both platforms:

1. In **Cloudflare Dashboard → Workers & Pages → gostop-authority → Settings → Variables and Secrets**, set the plain-text `ALLOWED_ORIGINS` variable to the exact Vercel production origin, such as `https://your-project.vercel.app`. This value is not secret. Localhost and loopback origins are always accepted for development.
2. In **Vercel Project → Settings → Environment Variables**, add `GOSTOP_SERVER_URL` with the Worker origin, such as `https://gostop-authority.your-subdomain.workers.dev`. Select **Production**, then redeploy. `vercel.json` runs `node scripts/write-runtime-config.mjs`, which validates the URL and writes it into public `runtime-config.js`; Vercel does not inject it automatically.
3. For Preview deployments, prefer a stable custom preview origin and add that exact origin to `ALLOWED_ORIGINS`. Otherwise, add each preview deployment's exact `https://...vercel.app` origin to the comma-separated value. Arbitrary `*.vercel.app` origins are intentionally not trusted.

No account ID, domain, route, credential, or API token is stored in source. The Worker URL is public configuration, while room credentials remain per-browser values in `sessionStorage` and WebSocket subprotocols; cookies are not used.

The Worker enforces an exact-origin allowlist on all room HTTP and WebSocket routes. JSON POST preflights allow only `POST` and `content-type`, return `Vary: Origin`, and are cached for one day. WebSocket upgrades must carry an allowed browser `Origin`; requests with missing or unrelated origins are rejected before Durable Object lookup.

This new, never-deployed Worker uses Wrangler's declarative `durable_objects.exports` lifecycle rather than a legacy migration tag. The `GameRoom` export explicitly selects `storage = "sqlite"`; the binding still maps `GAME_ROOMS` to that exported class. This avoids creating a historical migration chain before the first deployment.

## HTTP room API

* `POST /api/rooms` allocates the first seat and returns `{ roomCode, matchId, status, maxPlayers, playerId, seatId, credential }`. `matchId` is `null` while waiting.
* `POST /api/rooms/{ROOM_CODE}/join` allocates the second seat and creates the authoritative match. Supplying an existing room `credential` rejects accidental self-join.
* `GET /api/rooms/{ROOM_CODE}/ws` upgrades with WebSocket subprotocol `gostop-token.{credential}`.

Errors use `{ ok:false, error:{ code, message } }`. Seats, player IDs, match IDs, and 256-bit credentials are generated by the server. Only a SHA-256 credential digest is persisted. A credential proves temporary seat ownership on reconnect; it contains no state. Account IDs are reserved as nullable participant metadata for a future account/leaderboard milestone.

## WebSocket protocol version 1

Every JSON message contains `protocolVersion: 1`.

Client messages:

* `action`: `{ actionId, expectedRevision, action }`
* `syncRequest`: `{ sinceRevision }`
* `ping`: optional `{ nonce }`

Server messages: `connected`, `snapshot`, `actionAccepted`, `actionRejected`, `opponentConnected`, `opponentDisconnected`, `error`, and `pong`. Snapshot messages can include ordered viewer-visible `events`. Unknown versions, malformed payloads, unauthenticated sockets, stale revisions, conflicting IDs, out-of-turn actions, and illegal actions receive structured rejection/error messages.

The room derives `playerId` from the authenticated socket and calls `SessionAuthority.submitAction`; a client-provided seat, state, score, or winner has no protocol field. After acceptance, the room independently calls `getSnapshot` and `getEventsSince` for each participant. It never serializes `readTrustedState`, `exportMatch`, credential digests, or the room storage record.

## Persistence and reconnect

The object stores room metadata, participant/seat assignments and credential hashes, status, bounded action ordering metadata, structured terminal result, and the authority's JSON-safe serialized match. The authority record includes current game state, revision, event history, and action-id fingerprints/responses, so restart does not defeat idempotency. Animation and audio state are never stored.

Reconnecting with the credential replaces the prior in-memory socket and receives the current viewer-safe snapshot. `syncRequest` returns a stable snapshot plus ordered visible events after the requested revision. Disconnect only updates presence and notifies the opponent; it never forfeits.

This initial implementation uses standard Durable Object WebSockets. The socket registry is deliberately a participant map, and persistence is hibernation-safe, but WebSocket Hibernation event handlers are deferred until server hardening so correctness is not split between two socket paths.

## Browser authority boundary

Online mode never starts the AI scheduler. Its central local-mutation wrappers fail closed, and disconnect locks the table. Card play, floor target, Bomb blank, Shake/Keep, Bomb/decline, Go/Stop, Gukjin choice, opening resolution, deterministic turn-resolution steps, Nagari, and new-hand requests are sent as revisioned WebSocket actions. Server snapshots replace browser state, while viewer-safe semantic events enter the existing presentation functions. Solo continues to use its browser-local authority and AI unchanged.
